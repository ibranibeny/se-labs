# Deploy Azure Service Availability

Azure Service Availability is a dashboard that shows which Azure services, VM sizes
and Azure Managed Redis SKUs are offered in each region. The
[deployment guide](https://ibranibeny.github.io/azure-service-availability/deploy.html)
walks you through standing up your own copy. A single `bash scripts/deploy.sh`
run in Azure Cloud Shell (Bash, with the Azure CLI and Bicep already installed)
builds the whole backend in one resource group. You get two Python 3.12 Azure
Functions apps on the Flex Consumption plan, Azure Managed Redis, a locked-down
storage account, a virtual network with private endpoints, Application Insights
and two Microsoft Entra app registrations. GitHub Pages then publishes the
dashboard. The repository holds no secrets: every service-to-service call uses a
user-assigned managed identity.

The backend splits the work between two Function apps. The **collector**
(`func-asa-collector-*`) runs on a timer every six hours (`0 0 */6 * * *`, UTC).
It calls the Azure CLI with its managed identity, which holds Reader on the
subscription, and writes a fresh snapshot to Azure Managed Redis. The **API**
(`func-asa-api-*`) is a read-only HTTP endpoint for the dashboard. Guests can read
it without a token, and signed-in users from the allowed domains present a
Microsoft Entra ID token for the `Availability.Read` scope. Redis uses Microsoft
Entra authentication only and has public network access turned off. Both apps join
`snet-functions` through VNet integration. They reach Storage and Redis over four
private endpoints that resolve through private DNS zones linked to the VNet.

You need rights to create role assignments at subscription scope (for example
Owner, or Contributor plus User Access Administrator), permission to register
applications in Entra ID, and a region that offers both Flex Consumption and Azure
Managed Redis. Fork the repository, clone it into Cloud Shell and export a few
settings: `PAGES_URL`, `ALLOWED_DOMAINS`, `LOCATION` and `RG`. Then run the
script. It works in phases. It registers any missing resource providers and
creates or updates the API and dashboard app registrations. Next it starts the
Bicep deployment and, while Azure provisions, builds both zip packages locally
(52 MB for the collector, which carries the Azure CLI, and 7 MB for the API).
Once the deployment succeeds, it zip-deploys the code, triggers the first
collection and prints the `window.ASA_CONFIG` block for the dashboard.

Paste that block into `docs/config.js` in your fork. Then set GitHub Pages to
deploy from the `main` branch's `/docs` folder, and the dashboard goes live, with a
guest view and Entra sign-in. The guide's checks confirm that everything works:
`/api/health` returns `{"status":"ok"}`, and `/api/summary` returns 200 for guests
and 401 for a bad token, which is never treated as a guest. An Application
Insights query shows the `Collection finished` trace, and `scripts/inspect-storage.sh`
lists the storage account's settings, containers and role assignments through the
management plane without ever reading their contents. Further sections cover
day-to-day runs (for example `run-collector.sh` for an on-demand refresh, or
`APPS=none` reruns to change settings), troubleshooting (`finish-deploy.sh` resumes
after a Cloud Shell disconnect), and a clean-up that removes the subscription-level
Reader assignment, the resource group and both app registrations.

The most instructive part of the guide is **Why a storage account?** Every
Function app needs host storage (`AzureWebJobsStorage`). On Flex Consumption that
account holds each app's deployment package in its own blob container, the timer
lock and schedule status, and the function keys in blob storage, plus diagnostic
events in Table storage. The dashboard data itself lives in Redis. The account is
hardened the way Microsoft Learn recommends: public network access and shared-key
access are disabled, and apps connect with identity-based connections and
least-privilege data roles. Traffic stays on private endpoints for blob, queue and
table. The animated architecture below replays the guide's four storage flows hop
by hop: deploy and start, the timer run, keys and a manual run, and what you can
(and can't) see from outside.
